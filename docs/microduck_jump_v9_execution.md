# Jump V9 执行记录

日期：2026-09-25；基于 `6b4d385` 的未提交工作区。
对应 [训练前计划](microduck_jump_v9_plan.md)。本页不代表实机验收或完整训练完成。

## 已落实的修复

- V9 独立恢复完成事件，不伪造跳跃高度；恢复样本不安排请求。
- reset 与命令重采样共享同一次分类；拒绝请求事件跨 manager 调用顺序保留一次。
- 按名称解析腿/踝，明确选择两个脚 site；CPU/GPU 共用姿态测量函数。
- V9 缺失严格姿态输入直接报错；评估缺字段无效，未观察到的事件用 null。
- 首次请求同样执行严格 ready 门槛；多请求评估累计超时，超时后迟到完成不计有效跳跃，
  最终训练控制器也不补发迟到完成奖励。
- 脚/腿成本有界、pilot 使用较小质量权重；落地漂移事件按 dt 统一单位。
- worker 校验父模型 SHA，加载后覆盖并检查实际 optimizer LR；监督器只有一个
  续训指针，回滚更改的就是下个 worker 使用的指针。失败尝试的预算预留不会消失。
- V3–V8 原有测量/奖励路径保留；新语义由版本 9 显式启用。

执行期间补充发现：旧 `_jump_foot_posture_errors` 内创建的 `SceneEntityCfg`
没有经 manager 解析，默认 `site_ids=slice(None)`，因此将相机等全部 7 个 site
当作脚姿态来源。这是巨大脚姿态惩罚的直接原因之一。V9 明确选择
`left_foot` / `right_foot`，并新增带 180° 干扰 site 的回归测试。

当前脚 roll 定义是超过 HOME 标定约 5° 的部分，pitch 对地面计；这是角度代理量，
尚未增加足跟/足尖接触几何验收。当前纯恢复初态仍是低噪声近 HOME 合成状态，
不是从真实落地轨迹抽样；后续恢复课程需要补齐，不能将其成功率等同真实落地恢复率。

## 工程验证

- 全量 CPU 回归结果见 `preflight/tests.log`（增加训练数据门禁前为 296 passed、1 skipped）。
- GPU smoke：两次 64 env × 5 PPO update，最终一次包含超时奖励修订；
  每次 120 个 50 Hz 控制步，61D actor、14D action。两次均计账，合计 10 update。
- 实际 LR `5e-5`；奖励符号检查通过。smoke 仅 2.4 秒，未覆盖 7 秒跳跃请求，
  跳跃行为由独立完整回合评估与后续 50-update pilot 检验。
- 标准导出包含 normalizer；ONNX/PyTorch 129 组输入最大动作误差
  `1.5497207641601562e-6`（smoke-002），形状和 V9 元数据通过。
- 独立空 Warp 缓存的 GPU 构建与单跳步进完成，未复现 V8 历史编译异常；
  这不等于验证了全新依赖安装环境。
- 完整 CPU BAM 20 秒、7 秒请求一次，已保存未剪辑视频和每步严格测量；
  请求被接受，无身体触地/invalid，但恢复超时、严格完成 0 次。

CPU smoke 模型的落地后 8–20 秒诊断：躯干倾斜始终小于 3°，腿最大误差
始终大于 0.10 rad、脚 pitch 始终大于 3°，踝最大误差约 93% 时间超过 0.06 rad。
终值分别约 0.114 rad / 3.47° / 0.066 rad。已检查 8 秒及 18 秒关键帧；
没有逐帧人工审阅整段视频，不能据此声称完整视觉验收通过。

首次单跳诊断使用 15 秒窗口，发现截断最晚恢复，已延长至 20 秒后重测。
多请求超时累计修订前的结果保存在 `preflight/pre-timeout-latch/`，不用于选模。

## 当前实验与边界

原始数据在 `artifacts/jump-v9/`：`baselines/` 保存父模型 A/B 各 100 回合、
seed 123 的 standing/recovery/single/triple 和逐步轨迹；`smoke-001/` 保存模型、
ONNX、配置、源码快照、实际奖励积分；`preflight/` 保存测试与 CPU 视频。

| A，6375 | 100% | 95% | 12% | 0% | 47.33% |

所有以上样本的 failure/body-contact/invalid 均为 0。A 单跳恢复超时 88%，B 为 100%。
GPU 回放不保证逐位确定性；A 的一次前期重测单跳为 8%，冻结结果为 12%，
不能把几个百分点的变化直接解释为训练改善。旧基线中的恢复延迟仍可能报告迟到
的物理完成，但成功率已排除超时；后续控制器不再产生迟到完成事件，延迟分位数

最终达标。本轮先执行每分支 50 update 的检查边界。全局新增上限仍为 4000 update。

## 首块发现：训练数据门槛

A 的 50-update 训练块已完成；实际 LR 为 `5e-5`，parent SHA 与配置一致。
24 秒 rollout 内跳高/跳跃完成/纯恢复完成积分全部为 0，拒绝请求积分为
`-2.4130859375`，恢复超时为 `-0.408203125`。不能把“训练脚本跑通”当作技能学习。

继承的 actor 在无请求时仍使用非头部 0.05、头部 0.03 的动作空间探索标准差，
确定性评估则使用均值。新增零 PPO 更新的 `diagnose_jump_v9_readiness.py`
对照确定性与 1 / 0.25 / 0.10 倍 idle 噪声，量化训练门槛是否截断技能数据。
监督器新增数据门禁：请求窗口之后，存在拒绝但高度、跳跃完成、纯恢复完成
均为零时停下诊断，不自动扩大同一配方。

首轮 A/B 各 50 update 已完成（seed 123、每项 100 回合）：
A standing/recovery/single/triple 为 100% / 100% / 22% / 13%；
B 为 75% / 96% / 0% / 0%，单跳与三跳复测仍为 0%。B 因站立退化已回滚。
A 只是诊断候选：单跳恢复超时 78%，三跳最终漂移 P90 9.12 cm；尚未达标。
两分支训练期间高度/跳跃完成/纯恢复完成积分均为零，评估改善不能证明跳跃学习。
旧 state 的 A continue/B rollback 未体现后加入的数据门禁，已在续训前改为 diagnose。
